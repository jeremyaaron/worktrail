# Worktrail v0.3.0 UX Audit

Date: October 17, 2026  
Baseline reviewed: v0.2.9, commit `4e508cc`

## Assessment

Worktrail has a coherent foundation. The v0.2.0 consolidation and subsequent saved-view improvements made the existing navigation, work discovery, batch editing, and reporting easier to understand. The next nine releases added meaningful depth: cycles, portfolio review, closeout, parent/child work, pagination, files, Quick Find, and formatted discussion.

The resulting UX problem is mostly at the boundaries between those capabilities. Users can discover a risk without being able to correct it from the record, leave a review and lose their route back, see a historical count without being able to inspect all its evidence, or navigate between similar summaries whose numbers mean different things.

The v0.3.0 opportunity is to make the existing operating cycle continuous:

> Find the relevant work, understand its context, take the necessary action, and return to the review that prompted it.

This calls for focused workflow repairs and stronger information hierarchy. The existing scope supports a capable product; adding another dashboard or major feature area would increase the consolidation burden.

## Recommended Responsibilities

| Surface | Primary User Question | Best Next Step |
| --- | --- | --- |
| My Work | What needs my attention? | Open an item with its attention reason and return context |
| Inbox | What changed or requires my response? | Open the relevant discussion or record; manage read state separately |
| Work Items / Project Work | Which records match my criteria? | Inspect, refine, save the query, or explicitly batch-edit the visible page |
| Projects | Which project should I open? | Open a project; create one through a secondary command |
| Portfolio | Which project needs attention first? | Follow a specific health, communication, or execution signal |
| Project Overview | What is this project's current operating context? | Open its current cycle, planning review, or latest report |
| Planning | What needs a project-level decision? | Review current execution and delivery targets; open exact actionable work |
| Cycle / Milestone Review | What is happening within this scope? | Inspect the affected work and return to the same review |
| Cycle Result | What happened when this cycle closed? | Inspect complete historical evidence or deliberately open current context |
| Reports | What did we publish at a point in time? | Read or share a snapshot and deliberately follow links into current data |

These responsibilities can be expressed through ordering, labels, destinations, and available actions. They do not require an explanatory block on every page.

## Findings And Recommendations

### 1. Complete The Corrective-Action Loop For Planning Fields

Cycle review surfaces unestimated work and target points. Planning, My Work, and portfolio surfaces emphasize due dates and overdue work. The create form accepts both due date and estimate, and `UpdateWorkItemRequest` supports changing or clearing both. However, work-item detail displays them only as metadata: its edit form and update payload omit both fields. Project bulk edit can change due dates, but has no estimate action and is a maintainer workflow.

A contributor can therefore follow an unestimated-work signal to the correct record and still have no UI for supplying its estimate. Changing a single due date requires a detour through project bulk editing for actors who have that capability. This is the clearest gap between the current feature set and a complete daily workflow.

Recommendations:

- Add due date and estimate to the record's focused edit controls, including explicit clearing and the existing validation rules.
- Keep cycle, milestone, assignee, estimate, and due date together as planning facts. Show cycle in the read summary as well as the form/metadata; it is currently absent from the summary grid.
- Retain the distinct status-transition command and its permissions, while keeping it visually close to the other primary actions.
- Return the user to the originating review after the save, where the live evidence can reflect the change.

Acceptance: from Cycle Review, a contributor can open an unestimated item, assign an estimate, return, and see that item leave the unestimated group. An authorized user can change or clear a due date on one record without entering bulk mode.

Evidence: [detail form and metadata](../../apps/web/src/app/features/work-items/work-item-detail-page.component.ts#L160), [detail update payload](../../apps/web/src/app/features/work-items/work-item-detail-page.component.ts#L2546), [existing update contract](../../packages/contracts/src/work-items.ts#L263).

### 2. Protect Unsaved Authored Work Across Navigation

The v0.2.9 editor correctly preserves drafts after failed saves, and context generations prevent late responses from writing into the wrong record. Those are important protections. They do not protect the user from leaving a draft: routes have no deactivation guard, and detail resets description/comment state when the work item or actor changes. Create and report-draft pages also hold their edits in local form state.

Longer formatted descriptions and comments make accidental loss more expensive. Parent/child links, dependency links, global navigation, and Quick Find now provide many ways to leave while authoring.

Recommendations:

- Establish consistent leave behavior for changed descriptions, new comments, comment edits, work creation, and report narrative drafts.
- A scoped unsaved-change confirmation is a reasonable v0.3.0 baseline. Offer stay and discard choices; prompt only for meaningful changes from the loaded baseline.
- Cover same-component item changes and actor changes as well as route destruction. A route-exit guard alone will not address all current reset paths.
- If temporary draft retention is chosen, key it by workspace, actor, record, and authoring purpose. Preserve the existing stale-response and actor-isolation guarantees.
- Keep explicit cancel/discard behavior predictable, and do not imply a server-saved draft where only local text exists.

Acceptance: type a description and a separate comment, then attempt a parent/child navigation, a Quick Find jump, a global-page navigation, and an actor switch. Each transition either preserves the appropriate draft or obtains an explicit discard decision. Clean forms navigate without interruption.

Evidence: [route definitions](../../apps/web/src/app/app.routes.ts), [detail route changes](../../apps/web/src/app/features/work-items/work-item-detail-page.component.ts#L1556), [detail reset](../../apps/web/src/app/features/work-items/work-item-detail-page.component.ts#L2459), [report draft state](../../apps/web/src/app/features/projects/status-reports/project-status-report-draft-page.component.ts#L546).

### 3. Preserve Origin And Land At The Relevant Content

Work-list pagination and filters already survive detail return navigation. That good behavior is uneven elsewhere:

- Closeout unfinished-item links and historical closeout-item links omit `returnUrl`; detail falls back to project Work.
- Dependency links also omit the origin. Parent/child links use a bare `detailSelfUrl()`, so the chain back to the initial filtered list is lost after the intermediate record is revisited.
- Quick Find work-item and attachment destinations omit return context.
- Inbox links reach the record with an Inbox return URL, but do not target the comment/discussion associated with the notification.
- Cycle Review's Back to Planning link does not retain whether the user came from the Cycles management view. The safe return parser also drops fragments.

Users reviewing several records should not need to reconstruct their search or decision context after each inspection. Reaching the right record is only half of navigation; the relevant section and return path matter too.

Recommendations:

- Apply the existing safe local-return convention to closeout, historical results, dependencies, Quick Find, and creation success links.
- Preserve the original list query and page across parent/child inspection. Prefer a bounded origin plus immediate-parent context over indefinitely nesting return URLs.
- Use descriptive return labels such as Back to cycle review or Back to filtered work, instead of a generic Back wherever the destination is known.
- Extend the successful `#files` landing pattern to discussion and, where notification data identifies it, a specific comment. Make the target programmatically focusable and handle same-record navigation.
- Preserve the relevant Planning subview and distinguish an application return action from browser history.

Acceptance: page 3 of filtered Work -> parent -> child -> parent -> originating Work returns to the same query/page. Closeout -> unfinished item -> return reaches closeout. A mention notification lands at relevant discussion, and a Quick Find attachment jump retains its Files targeting and origin.

Evidence: [detail return target](../../apps/web/src/app/features/work-items/work-item-detail-page.component.ts#L1480), [detail self URL](../../apps/web/src/app/features/work-items/work-item-detail-page.component.ts#L1441), [closeout work links](../../apps/web/src/app/features/projects/cycle-closeout/project-cycle-closeout-page.component.ts#L122), [snapshot links](../../apps/web/src/app/features/projects/cycle-closeout/cycle-closeout-result.component.ts#L82), [Quick Find destinations](../../apps/web/src/app/features/quick-find/quick-find-navigation.ts#L95), [Inbox destination](../../apps/web/src/app/features/inbox/inbox-page.component.ts#L87).

### 4. Make Cycle Results Complete Historical Records

The closeout experience has a strong foundation: scoped evidence, explicit destination options, transactional completion, and a durable result. The result page clearly labels Snapshot and Live view. Keep those distinctions.

Two presentation choices weaken the result. Each historical item group shows only eight records and a message that additional records are not shown, with no expansion control. The existing snapshot arrays contain the evidence, but users cannot inspect all of it through this UI. A current filtered work list cannot replace historical evidence because assignments and fields may have changed.

The page also appends the full live cycle dashboard after the result. In the retained desktop capture, a completed result is followed by a 50% Complete metric, live target progress, scope breakdown, nine empty risk categories, and recent movement. The labels are technically explicit, but the page asks users to reconcile several different meanings of completion and commitment while scrolling through extensive empty content.

Recommendations:

- Let users expand or locally page through every group in the existing snapshot. Label current-record links separately from historical values.
- Make Outcome at close the dominant completed-cycle experience. Put current assignments and current risks behind a clear Current context disclosure or secondary view.
- Label live work progress as Work done, rather than letting Complete compete with the cycle's completed lifecycle state.
- Replace multiple empty risk blocks with one concise no-current-risks state; keep an option to inspect all categories when useful.
- Keep an obvious next step into the destination cycle or the carried items returned to unplanned work. Do not label a broad current-work view as the exact historical carryover set.
- For unfinished scope, require a deliberate destination choice or clearly distinguish the proposed default from a confirmed decision. Preview currently preselects the first eligible cycle, or unplanned work when none is available.

Acceptance: a cycle with more than eight unfinished items remains fully inspectable after closure and after those records change. The result makes closed-cycle outcome, work done at close, and current assignments distinguishable. A closeout decision visibly names the destination and affected count before submission.

Evidence: retained `result-desktop.png` and closeout preview captures; [snapshot truncation](../../apps/web/src/app/features/projects/cycle-closeout/cycle-closeout-result.component.ts#L78), [result/live composition](../../apps/web/src/app/features/projects/project-cycle-review-page.component.ts#L129), [default destination](../../apps/web/src/app/features/projects/cycle-closeout/project-cycle-closeout-page.component.ts#L351).

### 5. Make Risk Labels, Counts, And Drill-Downs Agree

Several small inconsistencies accumulate into uncertainty about what a review is saying:

- Cycle Review sums overlapping section counts and labels the result as items. A blocked, overdue, unestimated item can contribute several times.
- The Over target section contributes a count of one for a cycle-level condition, alongside counts of work items.
- Unestimated work links to all open cycle work: the query contains no estimate condition. The resulting list can include estimated records even when the review's group is specifically unestimated.
- Shared risk definitions carry milestone-specific descriptions into Cycle Review, including Work items in this milestone and In-progress milestone work.
- Planning's total also sums category memberships. Portfolio attention headers show the length of lists capped at five without identifying them as previews.

These are operational trust issues. The app should tell users whether a number represents unique work, risk occurrences, a scope-level condition, or a bounded preview.

Recommendations:

- Use unique item counts when the label says items; alternatively say risk signals and retain an explicit category breakdown. Keep cycle-level conditions separate from work-item counts.
- Make risk descriptions scope-aware. Cycle Review should consistently speak about cycle work; use neutral wording where one description is shared across scopes.
- Close the unestimated drill-down gap with a narrowly defined estimate-state query integrated into the existing filter/URL flow. Until that exists, label the broader action Review open cycle work rather than implying it reproduces the group.
- Treat Over target as a planning condition with Review cycle scope, rather than pretending it is a count of affected records.
- Mark capped attention sections as Up to 5 highlighted or Showing 5. Keep exact totals attached to the complete comparison/list where available.

Acceptance: one item matching three risk categories is never described as three distinct items. An unestimated drill-down yields the same scoped records in unchanged data. Cycle Review contains no milestone-specific risk copy. Portfolio preview counts cannot be mistaken for workspace totals.

Evidence: [risk definitions and unestimated query](../../apps/api/src/services/work-risk-sections.ts#L54), [cycle-level count](../../apps/api/src/services/work-risk-sections.ts#L207), [cycle total](../../apps/web/src/app/features/projects/project-cycle-review-page.component.ts#L1058), [Planning total](../../apps/web/src/app/features/projects/project-planning-page.component.ts#L1918), [portfolio cap](../../apps/api/src/services/portfolio-service.ts#L414).

### 6. Repair Portfolio Width Constraints And Improve Comparison

There is a concrete source-level width mismatch in the wide Portfolio comparison. Above the 1320px viewport breakpoint, a row has six grid tracks with minima totaling 1120px. Five 12px gaps and 32px horizontal padding make its minimum requirement 1212px. The application content shell is capped at 1120px, and the comparison panel uses `overflow: hidden`. The wide grid cannot fit its container as specified; right-side content is at risk of being clipped even when body-level overflow checks pass. The common-page overflow test currently omits Portfolio.

Fresh rendered reproduction is still required. The incompatible constraints are visible in the source and should be repaired before treating Portfolio as a release-ready comparison surface.

The broader usability issue is that comparison rows contain health reasons, four metrics, communication detail, two planning contexts, and up to eleven destination links. Four attention sections above them repeat some of the same projects. On mobile, these become a long sequence of expanded summaries and commands.

Recommendations:

- Base row layout on actual available container width. Ensure every action remains visible or has an intentional accessible overflow location.
- Prioritize project, health/top reason, active cycle or milestone, and report freshness in the scan row. Reveal secondary detail on demand.
- Give each row one signal-specific next action and a compact secondary action menu. Make metrics themselves useful drill-downs where appropriate.
- Keep attention previews short and identify their bounds. Add simple client-side health/freshness filtering over the complete returned project rows before inventing another data model.
- Preserve severity-first ordering, but make it easy to locate a named project or compare a selected concern.

Acceptance: at 1440px and wider viewports, the actual 1120px content region contains the full comparison and reachable actions. At 390px, a user can scan project health without opening every detail. Test child/control containment and clipping as well as body overflow.

Evidence: [comparison tracks and clipping](../../apps/web/src/app/features/portfolio/portfolio-project-comparison.component.ts#L109), [row destinations](../../apps/web/src/app/features/portfolio/portfolio-project-comparison.component.ts#L282), [shell width](../../apps/web/src/app/app.scss#L152), [current viewport coverage](../../e2e/worktrail-smoke.spec.ts#L1727).

### 7. Rebalance Work-Item Detail Around The Current Task

The read summary and rendered description at the top are valuable. Below them, the page renders parent management, any child list, the entire detail editor, dependency lists and relationship creation, files, discussion/watchers, and history. Parent search is present even when no parent change is intended; the description appears again in the permanent editor. The retained desktop capture shows the empty parent manager consuming a substantial band before the main action area. Mobile turns the same order into a long reading path.

Recommendations:

- Keep identity, readable description, planning facts, status, and a compact watch action immediately available.
- Enter the description/details editor through Edit. Avoid presenting the same description as both rendered content and an open source editor by default.
- Show the current parent as context; open candidate search through Set parent or Change parent. Keep structural-ineligibility guidance near that command.
- Keep child-work progress compact by default, with expansion and the existing View all child work link. Preserve flat two-level navigation.
- Put discussion within easy reach through a local section navigation or anchored jump. Place files and dependencies alongside that navigation; surface urgent blockers near the primary actions.
- Collapse relationship creation, watcher lists, and history when the user is reading or responding. Keep file capacity, retry, removal confirmation, and archive restrictions available when needed.

Acceptance: opening an item to read or reply does not require traversing parent search, the full edit form, and empty relationship controls. Opening it to change status exposes that command near the read summary. Files deep links remain functional.

Evidence: retained summary and mobile comment captures; [detail section order](../../apps/web/src/app/features/work-items/work-item-detail-page.component.ts#L101), [parent manager](../../apps/web/src/app/features/work-items/components/work-item-parent-manager.component.ts#L23), [child summary](../../apps/web/src/app/features/work-items/components/work-item-child-work.component.ts#L50).

### 8. Put Current Execution First In Planning

Review, Cycles, and Milestones already have a URL-backed view choice. Preserve it. The Review surface nevertheless begins with repeated project identity and a substantial report-promotion block before the review control and evidence. Health, cycle summaries, milestone progress, shortcuts, review sections, and risk sections then accumulate vertically. Cycles management leads with a full creation form, and existing cycle rows expose editing fields.

Recommendations:

- Start Review with a compact project-health summary and the active execution focus. Place the active cycle and its end date/unfinished scope ahead of upcoming and completed context.
- Move the report bridge into a compact contextual Draft report action with a secondary Reports link. Preserve explicit live/snapshot labeling where evidence changes meaning.
- Group milestone delivery targets separately from execution windows, and show the most relevant item before the complete collections.
- Turn zero-risk categories into one quiet state or an optional disclosure. Keep populated categories and their exact drill-downs prominent.
- Lead Cycles and Milestones management with existing records. Open creation and per-record editing deliberately, retaining validation and role restrictions.
- Give a missing active cycle a useful next step: review planned cycles or create one when authorized, rather than leaving an isolated empty summary.

Acceptance: a maintainer can locate the active cycle, its main risk, the corresponding work, and the closeout entry without first traversing report explanation or creation forms. Contributors get useful review content without a disabled administrative interface dominating it.

Evidence: [Planning header and report bridge](../../apps/web/src/app/features/projects/project-planning-page.component.ts#L110), [review composition](../../apps/web/src/app/features/projects/project-planning-page.component.ts#L374), [cycle summaries](../../apps/web/src/app/features/projects/planning/cycle-summary-panel.component.ts#L22), [cycle management](../../apps/web/src/app/features/projects/planning/cycle-manager.component.ts#L40).

### 9. Make Saved-View And Pagination State Understandable

The compact saved-view opener and disclosed management are improvements. However, the selected opener value and Opened message are component-local state, not a declaration that the current applied query still equals that view. Filter changes can leave the last-opened name/message on screen, while pinned shortcuts use a separate event path. Pagination controls are below the entire result set, including when the user wants to change page size before scanning 100 rows.

Recommendations:

- Show a current-view identity derived from the applied filter/sort state: a selected named view, Modified view, or Custom view. Do not let an opener selection or an old success message stand in for applied state.
- Make pinned shortcuts and the opener share that feedback. Confirm that results loaded successfully before claiming they were updated.
- Keep save/update actions close to that identity, with a readable query summary when changing a shared view.
- Put range, total, page size, and compact previous/next controls near the result heading. Retain bottom navigation for long pages and the existing result-focus behavior after page changes.
- Continue treating saved queries separately from transient page state. A saved view should still open at page 1 with the documented default page size.
- Keep visible-page selection explicit. Announce selection clearing on page/query changes when it occurs, and ensure selected counts/actions are reachable on mobile.

Acceptance: opening a view and changing a filter never implies the saved view itself was changed. At 100 rows per page, page navigation and page-size controls are available before scrolling to the bottom. Returning from detail still restores the applied query and page.

Evidence: [saved-view feedback](../../apps/web/src/app/features/work-items/components/saved-views-toolbar.component.ts#L629), [pinned shortcut path](../../apps/web/src/app/features/work-items/components/pinned-saved-views.component.ts#L20), [result/pagination order](../../apps/web/src/app/features/work-items/workspace-work-item-list-page.component.ts#L382), [pagination control](../../apps/web/src/app/features/work-items/components/work-item-pagination.component.ts#L17).

### 10. Give New Routes A Stable Place In The Shell

Cycles, closeout, and milestone review belong conceptually to Planning, but their paths are siblings of `/planning`; the shell's route-prefix active link therefore does not identify Planning on those screens. Work-item detail lives outside the project shell, and its summary lacks a named project link. Quick Find determines current-project destinations from route `projectId`, so those destinations disappear on a work-item record even when its project is known.

The shell also repeats project identity that child pages render again. Mobile closeout captures show global navigation, actor tools, a full project header, project navigation, and page identity before scope evidence. The layout reflows, but its vertical cost remains high.

Recommendations:

- Give cycle, milestone, and closeout routes explicit Planning ownership in active navigation and breadcrumbs, without changing their established URLs.
- Make the shell the primary project identity. Child pages should name their task or record, such as Planning, Cycle name, or Report title, using a consistent heading hierarchy.
- Add a compact named project link on work-item detail. Make known record context available to Quick Find's project destinations.
- Prioritize daily destinations and search in the global shell; put Workspace Settings in a predictable utility location. Preserve access for contributors who can inspect read-only information.
- Compact the mobile project header and repeated descriptions after the first project entry. Keep the current section identifiable in horizontally scrolling navigation.
- Make Projects primarily a searchable directory. Move its full create form behind Create project; Portfolio should remain the operating comparison surface.

Acceptance: cycle review and closeout visibly belong to Planning. A user entering a work item through Quick Find can identify and open its project. At 390px, project context and the page's primary content do not require repeated full project introductions.

Evidence: [shell section matching](../../apps/web/src/app/features/projects/project-shell/project-shell.component.ts#L333), [route structure](../../apps/web/src/app/app.routes.ts), [Quick Find project context](../../apps/web/src/app/app.ts#L155), [Projects creation-first layout](../../apps/web/src/app/features/projects/project-list-page.component.ts#L36), retained mobile closeout capture.

### 11. Explain Work Breakdown Consistently

The two-level model is useful and intentionally keeps each record independent. Its presentation needs to help users avoid assumptions learned from tools with automatic rollups.

The shared child summary calls done plus canceled children complete. Cycle percentage, in contrast, uses done divided by total. Parent direct estimates and child points are separate, and cycle totals sum the estimates of assigned records. Both a parent and its children can therefore contribute their own estimates when assigned to the same cycle. Those are valid domain choices, but the UI does not consistently expose the distinctions at the point where users interpret progress.

Recommendations:

- Use separate Done and Canceled values, or call their combined total Closed. Reserve delivered/done language for successful completion.
- Label Parent estimate and Child estimate total distinctly. Make it clear that neither overwrites or automatically rolls into the other.
- Keep the existing notice that child cycle/milestone assignment is independent. Add concise local context when users assign or review a mixed parent/child scope.
- Clarify that a completed parent may still have open children, and containment itself is not a dependency.
- Make child summaries lead to the exact direct-child list. Keep parent context visible without turning every list or board into a tree.

Acceptance: a parent with one done and one canceled child does not imply two delivered children. Users can explain why a parent's estimate differs from its child total and why cycle scope may count both records.

Evidence: [child completion label](../../apps/web/src/app/shared/work-items/work-item-hierarchy-display.ts), [cycle percentage](../../apps/web/src/app/features/projects/project-cycle-review-page.component.ts#L974), [cycle estimate sum](../../apps/api/src/services/cycle-review-model.ts#L46), [documented independence](../v0.2.5/release-notes.md#L41).

### 12. Make Quick Find Limits And Continuation Useful

Quick Find is a valuable addition: bounded groups, explicit lifecycle labels, keyboard navigation, loading/error states, and attachment targeting all fit the product. It also adds a second search entry point whose expectations need to remain understandable.

Non-work-item groups stop at five records with More matches exist and no continuation action. Search disappears when the dialog closes. Excerpts reflect stored source, which can now include Markdown. The generic Search Worktrail label can suggest a broader search than is implemented; comments, full report bodies, and file contents are outside the search scope.

Recommendations:

- Retain Quick Find as the fast jump surface and Work Items as the complete paged work-discovery surface.
- Replace passive overflow messages with a useful refinement action or contextual guidance. Only offer View all where a real destination supports the same search semantics.
- Preserve the current query while a user briefly inspects a result and returns, within the same actor/workspace context. Keep this distinct from persistent search history or personalized ranking.
- Make filename results visibly different from file-content search, and use a concise empty-state hint when a search cannot find discussion or other unsupported content.
- Keep excerpts readable and escaped. Do not turn result snippets into another full Markdown renderer; any future plain-text projection should preserve the underlying source-search behavior.
- Keep archived/completed labels, focus restoration, bounded reads, and the existing Files landing behavior intact.

Acceptance: a user understands what to do when a group has more than five matches, can inspect two candidates without unnecessarily retyping the same search, and does not mistake a filename match for indexed file contents.

Evidence: [overflow UI](../../apps/web/src/app/features/quick-find/quick-find-dialog.component.html#L184), [group construction](../../apps/web/src/app/features/quick-find/quick-find-display.ts#L40), [search scope](../v0.2.8/release-notes.md#L43).

## Smaller Refinements

- **Authored content:** keep plain text/Markdown choice and source preview explicit. In ordinary reading, hide authoring controls until Edit. Formatting behavior should not require users to understand the parser profile before writing a short comment.
- **Mentions:** selected members are notification recipients; typed `@name` text is not. Keep explicit recipient chips near submission and make that distinction clear where users choose recipients. Preserve the rule that editing comment text does not silently change recipients or resend mentions.
- **Inbox:** preserve its event/read-state role and My Work's action-queue role. Group repeated events for the same record once volume makes individual cards repetitive; prioritize discussion landing before adding another notification filter system.
- **Status reports:** keep editable narrative and generated evidence visually distinct, protect local draft text, and retain the published snapshot/share behavior. Broader Markdown authoring for reports can be a later product decision; consistency does not require changing every text field's format in v0.3.0.
- **Files:** preserve the strong bounded upload, retry, capacity, archive, and removal states. Improve access from record navigation before adding previews, inline embeds, or new file-management surfaces.
- **Accessibility:** give navigation an active-page announcement, expose selected states for Inbox/Project filters, and complete the work-list table's row/header/cell semantics. Existing `role="table"`/`role="row"` markup leaves header and data spans without explicit cell roles. Validate announcements and mobile reading order with an actual screen reader.
- **Copy:** remove residual MVP language from primary workflows; use consistent sentence casing for statuses and concise task labels. Distinguish cycle completed, work done, work canceled, and snapshot values wherever they can appear together.

## Suggested Delivery Sequence

1. **Repair task completion and trust.** Add estimate/due-date detail editing; protect drafts; fix missing return targets; expose complete closeout evidence; correct scope copy, risk labels, and misleading drill-downs; repair Portfolio's width constraints.
2. **Consolidate the main operating surfaces.** Disclose detail editors and parent/dependency administration; simplify completed-cycle current context; reorder Planning; compact cycle/milestone management and portfolio comparison.
3. **Polish continuity and orientation.** Add current-view identity, top result controls, Planning route ownership, record project context, useful Quick Find continuation, and reduced mobile header repetition.

These changes can preserve established URLs, saved-query semantics, the complete unpaged board, explicit visible-page bulk editing, two-level hierarchy, bounded search, and immutable published/closeout evidence. The focused estimate-state filter is an identified query addition; most other recommendations use capabilities and data already present.
